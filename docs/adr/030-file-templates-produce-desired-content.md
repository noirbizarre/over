# ADR-030: File templates produce desired content and generated Git snapshots

**Status:** accepted

## Context

One tracked configuration template must support different machines without
rewriting its source. Symlinks cannot expose raw Jinja, and virtual checkouts
must remain physical files while retaining editable local changes.

## Decision

Extend existing hierarchical ordered rules with independent `template` and
`strip_extension` booleans. Resolve overlay dependencies/data once before rendering
using the existing cascading and recursive-merge semantics. Freeze the
data/environment inputs and use the shared strict MiniJinja infrastructure.
Templates consume data and never produce it for another template.

Desired state carries generated bytes, transformed destinations, original source
identity, and rendering identity. Byte-bearing debug output is redacted. Symlink
materialization atomically publishes reconstructible artifacts under XDG state.
Directory links containing transformations expand into leaf materializations.

A generated virtual checkout retains one ownership unit with a complete desired
leaf inventory. It reads committed source `HEAD`, writes physical target files,
and stores complete generated desired trees in local Git commits under
`refs/over/generated/<checkout-id>`. New commits parent the previous generated
snapshot. Source-only checkouts retain their existing source-index workflow.
Operational XDG metadata records identities, provenance, refs, conflicts, and
publication progress, never duplicate snapshot file contents.

Three-way reconciliation compares previous desired, physical local, and current
desired content. Safe textual merges preserve local edits. Conflicts preserve
the original local file and retain the original base in metadata even after the
desired ref advances. Explicit restore accepts the generated desired snapshot.
Publication uses path revalidation, ref matching, and metadata-only recovery
information. Reporting uses the same analysis without publishing objects/refs.

Generated destinations cannot flow back into ordinary source staging or Absorb.
The #276 follow-up adds conservative reverse patches during `over commit`:
recorded rendered changes map only to uniquely identified literal source content,
with disjoint source changes preserved and incompatible hunks reported per file.
This does not invert Jinja expressions or control flow. Only translated source
templates enter the source commit; physical rendered files remain untouched.

Partial reverse commits record per-destination source revisions. A journal ties
generated checkpoint publication to the planned source commit, so retrying can
finish metadata publication without a duplicate source commit. An additional
Git-backed consumed-render snapshot distinguishes already-recorded edits from
independent source changes still awaiting sync. Generated commits retain these
snapshots through parent links; XDG metadata continues to contain identities only.

## Consequences

Rendering is deterministic for fixed source/inputs and leaves source templates
untouched. Context-only changes can update a checkout without a source commit.
Local modifications are distinct from generated desired history.

Generated snapshot entries inherit source encryption policy, including ordinary
siblings. A versioned commit-message manifest retains per-entry provenance without
reserving a destination filename. Shared strict storage boundaries encrypt before
persistent blob publication and authenticate before plaintext reconciliation or
reverse patching. Both desired and consumed-render snapshots use this boundary.

Lock/unlock migrate known legacy snapshots recoverably, retaining a ledger of
leaked object IDs until actual object cleanup is verified. Unknown historical
ownership blocks completion; output without affirmative public-source evidence is
conservatively encrypted rather than silently classified as public. Key-independent
legacy comparisons do not certify inherited history through a new manifest.
Key rotation refuses to strand operational protected snapshots.

Rendered physical artifacts and snapshots from unprotected sources may contain
plaintext secrets. Local refs themselves neither encrypt nor protect content;
explicit refspecs or mirror pushes can publish the generated namespace. Over does
not configure automatic publication. Removing a ref does not securely erase its
objects.
